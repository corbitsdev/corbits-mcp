## 2. Deliverables and dependency direction

Four supported entries:

| Entry                             | Responsibility                                                                                            | Runtime dependency boundary                                                        |
| --------------------------------- | --------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| `@corbits/mcp/client`             | Standalone MCP client; existing client functions, transport, typed continuations and extension operations | No agent, hub, DB, Hono or credential-store runtime import                         |
| `@corbits/mcp/server`             | Fetch-compatible MCP server, registry, HTTP binding, server-side extension providers and security hooks   | No mandatory Interchange or OAuth-provider implementation                          |
| `@corbits/mcp/interchange/client` | Remote MCP → Interchange tool factories and host services for prompts/resources, MRTR/tasks/skills        | Uses actual agent/harness contracts and mediated handles                           |
| `@corbits/mcp/interchange/server` | Selected Interchange operations/tools/agents/workflows → MCP provider bindings                            | Explicit selection and identity mapping, never automatic exposure of the whole hub |

Dependency graph: `protocol` ← `client` / `server` / `extensions`; `interchange/*` composes those. Extension runtimes receive transport/registry interfaces; they do not import client facades and create cycles. Both roles consume the same wire validators, dialect validator, result applicability table, header codec and error taxonomy. Provider-specific validation supplements but never forks protocol validation.

Existing root, `./sidecar-bundle`, and `./hub` exports remain compatible façades. Existing root names, signatures, qualified names, credential declaration identity, bundle ID, stored catalogs, synchronous bundle construction and destructive ask floor remain intact. Root can keep its historical agent dependencies; the new standalone subpaths must not inherit them. Keep old extension functions as aliases if their canonical implementation moves. Security corrections can reject previously accepted malformed inputs: enumerate these in migration notes rather than silently preserving unsafe behavior. Do not rename MCP methods or extension IDs to `v2`.

No separate skills entry is necessary: wire APIs belong to client/server and verified host integration belongs to interchange/client. Keep filesystem-specific implementations behind explicit server imports/factories; do not pull filesystem code into the client entry.

## 4. Shared contracts to freeze before fanout

These are **proposed local APIs**, not existing `@intx` exports. Names below are the implementation contract; source files own them once implemented. Type details must be derived from the pinned wire schema, not copied independently into both roles.

1. `src/protocol/types.ts`, `schemas.ts`, `methods.ts`, `headers.ts`, `errors.ts`, `json-schema.ts`, `extensions.ts`, `index.ts`.
   - One `McpMethodMap` associates each method with params, ordinary result, allowed polymorphic results, required capability, cacheability and HTTP name source.
   - MRTR allowed only on `tools/call`, `prompts/get`, `resources/read`; task results allowed only on `tools/call` for the pinned tasks revision. All others accept complete results only. Unknown resultType is invalid everywhere, including subscription termination.
   - Name sources: tool/prompt name, resource URI, and **taskId for all three tasks RPCs**. Extension methods use their actual specification rules; do not invent name headers by analogy.
   - Shared `validateRequest`, `validateResult`, `validateNotification`, `validateSchema`, `validateInstance`, `encodeHeaderValue`, `validateRequestHeaders`. Validation context includes protocol era and opted-in extension settings. Keep unknown metadata/schema vocabulary where allowed; never erase metadata simply to satisfy a validator.
   - `FetchLike` is a structural fetch signature in the protocol/client layer, not an Interchange runtime dependency. Shared `McpError` retains existing fields/API and distinguishes local failure from peer JSON-RPC errors.
   - Add bounded AJV 2020-12 validation (and explicitly registered supported older dialects if needed); schema object validity and data validity are separate. No implicit network `$ref` resolution. Never use an unknown-keyword strictness setting that rejects valid 2020-12 extension annotations. Add depth/subschema/data limits before compilation.
2. `src/client/transport.ts`: internal `McpRequestTransport.request(method, params, options)` and `.listen(filter, observer, options)`; options include abort, timeout, progress, protocol era, extension settings, schema context and injectable fetch. Existing public functions delegate to this. Extension runtime functions accept this interface; façades preserve existing signatures.
3. `src/server/contracts.ts`: `McpServerOptions`, `McpRequestContext`, `McpProviders`, `McpOperationOutcome`; `createMcpServer(options)` returns `{ fetch(request): Promise<Response>, close(): Promise<void> }`.
   - Context has authenticated host identity, request ID, protocol version, client capabilities, signal, and scoped `reportProgress`; identity does not come from caller-controlled params or clientInfo.
   - Providers cover tools, prompts, resources/templates, completion, and subscriptions. Outcome is a discriminated complete/input-required/task union validated centrally. Extension providers plug into the same registry.
   - New modern HTTP server handles no implicit session state. A separately gated legacy HTTP shim handles `initialize`/initialized and supported old versions for compatibility, with capabilities restricted to behavior actually implemented. Never put modern tasks/MRTR on a legacy wire.
4. `src/auth/contracts.ts`: `McpAuthPolicy.authenticate(request)` returns validated `{ tenantId, principalId, scopes, authorizationContextId }`; `authorize(identity, operation)` checks selected resource/action. Policy can support intentional public mode, but sensitive adapters require authentication. `authorizationContextId` partitions caches; it is host-assigned and never a raw bearer.
5. `src/extensions/tasks/contracts.ts`: `McpTaskStore` with durable create/get/atomic compare-and-swap update and expiry, plus `McpTaskExecutor` with start/recover/submitInput/requestCancel. Records bind tenant, principal, original method/params, revision, outstanding/answered input keys, backend correlation, status, timestamps, TTL, result/error, and cancellation intent. Store durability precedes returning a handle. Never serialize callbacks or rely on a surviving Promise.
6. `src/interchange/server/contracts.ts`: `InterchangeExposure` explicit bindings for named tools, selected HTTP operations, agents, and workflows. Each binding supplies MCP definition, authorization resource/action, execute adapter, and applicable continuation/task hooks. HTTP selectors use `(method,path)` or a unique declared operationId, never guessed IDs. Identity/tenant/path constants are host-bound, not model-overridable.
7. `src/interchange/client/contracts.ts`: `McpHostServices` supplies user-facing elicitation, task persistence/status, resource/prompt presentation, verified-skill activation and policy callbacks. Missing service means capability is absent or a typed unsupported result, never implicit approval. Host callbacks do not change the wire vocabulary.
8. `src/extensions/skills/contracts.ts`: origin-scoped skill entry/held-manifest, approval receipt, verified bytes and acting-window lease. `McpSkillHostPolicy` must bind provenance and approval to model-context admission and all code-execution tools during the lease. A resource read is not skill activation. Pure verification can return verified bytes without claiming host activation.

## 5. Real Interchange bindings

Verified against `packages/agent/src/{index,tool,definition,agent}.ts`, `packages/harness/src/credential-capability.ts`, `packages/hub-api/src/{app,routes/runs,routes/workflows}.ts`, `packages/hub-client/src/workflows.ts`, and installed declarations/JS:

| Upstream surface                                                                                                                                     | Correct bridge use / limitation                                                                                                                                                                                                                                                                                                                      |
| ---------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `defineTool`, `AnnotatedToolFactory`, synchronous `factory(env): ToolBundle`; `ToolBundle.definitions`, `.run(call,signal)`, optional `.dispose()`   | Retain stored-catalog synchronous construction. Factory is evaluated only with authorized host env. Bare ToolBundle.run is a dispatcher, not an authorization boundary: MCP exporter explicitly checks grants first. Never instantiate every registered factory to discover arbitrary tools                                                          |

Signal drops queued work or rejects an active waiter; **the active reactor cycle keeps running**. Never close a shared agent as per-call cancellation. Use dedicated workflow run cancellation where termination is required; describe cooperative intent truthfully |
| `BaseEnv.authorize(resource,action,context)` and plugins                                                                                             | Host can compose a skill acting-window authorization gate with existing grants. No inspected export provides a turnkey remote-skill activation API. | CredentialCapability.resolve(handle), origin-pinned `http` handle, rotating material source                                                          | Agent sees the mediated handle only. Maintain per-tool credential consumer identity, grant checks and origin binding. Never return raw secrets through model context, tool results, tasks, telemetry, or skill caches                                                                                                                                |
| Hub `/openapi.json`; Hono app through exported `createApp`/`mountHubRoutes`                                                                          | Use explicit operation allowlists against provided OpenAPI or authored bindings. Invoke the host-authenticated route/application pipeline, not private route functions or fabricated registration helpers                                              |
| `/api/tenants/:tenantId/workflows/:runId/mail` (POST), `.../:runId/signals` (POST), `.../:runId/runs` and `.../:runId/runs/:eventRunId/events` (GET) | Actual hub-client helpers: triggerWorkflowRun, deliverWorkflowSignal, listWorkflowRuns, readWorkflowRunEvents. Hub-client is not currently installed: avoid adding it merely to make these HTTP calls; use the same verified routes via injected fetch, or deliberately add/test it through the integrator                                           |
| `/api/tenants/:tenantId/workflows/runs/:runId` (GET/DELETE), `.../events` (GET), `.../mail` (POST), `.../lifecycle` (GET)                            | DELETE requests durable cooperative cancellation; may return 202/409/503. Events are full seq-ordered snapshots: deduplicate by seq, do not assume SSE. Trigger returns runId/address/messageId, not a completed agent answer                                                                                                                        |
| Workflow signals require runId/signalName/signalId and optional correlationId; approvals have dedicated resolution semantics                         | `tasks/update` only forwards to configured outstanding input bindings, with stable IDs. Workflow invocation uses an explicitly configured deployment/run and result selector. For isolation, prefer a dedicated run per invocation; if sharing a run, the host must provide a proven message/correlation-level result selector. Never report all run events as the result of one invocation. Durable task records store run/message/signal correlation. Persist dispatch intent before executing; reconcile ambiguous crashes, never automatically replay a non-idempotent mail trigger and promise exactly-once execution.

Route projection is explicit and finite: reject ambiguous IDs, traversal, unsupported body/content-type/stream shapes, undeclared security overrides, and unresolved schema references before exposure. Read-only routes may optionally become resources; mutation/invocation routes become tools. Prompts/resources/skills do not silently become new grantable tools. Catalog visibility and execution authorization use the same bound identity; execute always rechecks authorization.

## 6. Maturity and compatibility policy

Registry records `{ id, coreRevision, extensionRevision, sourceCommit, maturity, enabledByDefault:false }`. Known baseline: tasks stable 2026-07-28; skills stable source snapshot above; Apps released 2026-01-26. Package version/SDK generation is not extension maturity.

- Stable upstream capabilities get ordinary local API names. An actual draft/experimental capability, if deliberately implemented, gets `unstable_` local exports/config plus explicit source pin and migration policy. The wire still uses the upstream identifier and settings exactly.
- No invented `/v2` methods, `-v2` extension IDs, protocol-version strings or task statuses. Existing unsupported/unknown extension settings fail clearly or remain unadvertised.
- Legacy client negotiation remains supported for the versions already documented by this package. New server legacy shim initially targets 2025-11-25, 2025-06-18 and 2025-03-26 Streamable HTTP only as tested. Legacy extension generations are not silently converted into modern ones. No claim that SDK 1.30.1 verifies modern 2026 behavior.
- Deprecated roots/sampling/logging are distinguished from core-required behavior: do not newly advertise them. MRTR parser recognizes standard requests and rejects unsupported capabilities safely. Keep existing DCR as deprecated compatibility fallback; prefer pre-registration/CIMD. Form/URL elicitation is in scope through explicit host hooks.

## 7. External dependencies and deployment gates

1. Add `ajv` 8.x, with optional `ajv-formats` if required by the chosen validation policy, and a bounded YAML parser (e.g. `yaml` 2.x) through CL-11478. Pin installed versions in lockfile and test Node 24 and Bun. Do not add MCP SDK to runtime solely for schema validation. Preserve licensing/provenance of copied upstream definitions.
2. oauth-core **already** exposes `OAuthClientConfig.resource`, and token/refresh helpers consume it. Fix `mcpClientConfig` locally to set it; extraAuthorizeParams.resource alone is insufficient. oauth-core callback-server returns only a code; its stock provider helper cannot validate callback iss. Existing `startOAuthLogin` accepts an injected `startCallbackServer`, so implement an issuer-validating local callback adapter and reuse OAuth exchange/state/PKCE machinery. A convenience hook upstream is optional, not a blocker for this PR.
3. No external Interchange repository edit is required for selected routes, tools, basic agents/workflows, mediated credentials, or verified skill host integration through explicit callbacks. Deploying the bridge still requires the host to mount it, bind identity/grants, configure lifecycle/dispatch services, and wire UI/context/approval hooks. Missing services must be reported unavailable, not fabricated.
4. Strong per-cycle cancellation of an existing shared in-process Agent is unavailable in 0.5.0. An upstream companion change is necessary **only if that stronger guarantee is demanded**. MCP cooperative task cancellation does not require it; expose the limitation and use dedicated workflow runs when stopping actual work matters.
5. Production durable task-store choice was asked of the director and remains unspecified. Default plan: injected atomic durable store contract plus an opt-in, restart-tested single-host file-backed reference store. Use an exclusive writer lock, atomic durable writes and explicit recovery; do not claim multi-host support for it. The host supplies a distributed adapter for multi-replica deployment. Test-only memory storage must never satisfy the production task-advertisement gate.
6. A durable store is insufficient without a recoverable executor. On restart reconcile backend operations and persist a truthful terminal failure when recovery is impossible; never leave a fake runnable task or replay non-idempotent effects blindly. Companion host persistence wiring is a deployment dependency, not an external edit folded into PR28.

## 8. Non-goals and deliberately deferred scope

This PR does not implement an authorization server, a browser/iframe Apps renderer, a general workflow engine, inference/sampling service, arbitrary OpenAPI compiler, blanket exposure of all hub admin routes, unapproved skill script execution, a distributed task database, or automatic grant widening. It does not add stdio/subprocess management, removed HTTP+SSE transport, SSE redelivery/resumption, deprecated roots/sampling/logging features, proprietary Claude channels, or old tasks-generation compatibility. Modern Streamable HTTP is the supported transport for both roles; transport-independent contracts keep a future stdio binding possible without implying it ships now. No external-repository edits, commits, pushes or issue creation are part of this planning deliverable. Full Apps-host, host-runtime, and product-wide “100% MCP compliance” claims are out of scope; compliance claims must be role-, revision-, transport-, capability- and test-qualified.
